# Build Blueprint Layer (Session 14)

The Build Blueprint makes a Product Document Pack **implementation-ready**.
Designers get screen-level logic; developers get API/screen/data/permission
mapping; AI coding agents get an implementation-ready bundle so they do **not**
need to invent product logic, screen logic, workflows or backend/API structure.

Everything is derived deterministically from the same canonical `PackContext`
(features → screens → entities → endpoints), so the blueprint is consistent with
the rest of the pack **by construction**.

## What the blueprint contains

Generated by `buildBuildBlueprint(ctx)` (`apps/api/src/packs/blueprint.ts`):

1. **Screen Logic Specification** — for every screen: purpose, user intent,
   entry/exit points, primary/secondary actions, data shown/required, states,
   permission rules, validation rules, backend & AI dependencies, edge cases,
   analytics events, microcopy, components, state transitions and acceptance
   criteria.
2. **State Matrix** — for each screen, which canonical states it specifies:
   `empty, loading, success, partial_data, weak_evidence, contradiction,
   low_confidence, permission_denied, llm_key_missing,
   source_configuration_needed, failed, locked_read_only`.
3. **API-to-Screen Mapping** — screen → endpoints (reads), actions → mutations
   (writes), and error → UI-state mapping.
4. **Component Contracts** — purpose, props, states, interactions, validation,
   accessibility notes.
5. **Permission Matrix** — role → allowed/blocked actions and UI behavior when
   blocked (consistent with RBAC).
6. **Analytics Event Map** — event, trigger, properties, related screen and the
   product question it answers.
7. **DO_NOT_BUILD** — explicit out-of-MVP exclusions and things AI coding agents
   must never invent (app generation, gradients, chat-first UX, direct provider
   calls, fabricated TAM, scope expansion).

## Build Readiness Score

`computeBuildReadiness(blueprint, opts)` returns a 0–100 score **separate** from
Opportunity / Confidence / Venture Scale, across six dimensions:

| Dimension | Weight | Checks |
|-----------|--------|--------|
| `screen_state_coverage` | 0.25 | Every screen has empty/loading/error |
| `api_screen_mapping` | 0.25 | Every endpoint is consumed by a screen |
| `acceptance_criteria` | 0.20 | Every screen has acceptance criteria |
| `permission_coverage` | 0.10 | Roles have explicit allowed/blocked actions |
| `scope_boundary` | 0.10 | DO_NOT_BUILD exists |
| `evidence_grounding` | 0.10 | Blueprint is evidence-backed |

Warnings are surfaced for any failing dimension.

## Quality gates (additive)

When a blueprint is present, the quality gates add:

- `screen_states_complete` — every screen has empty/loading/error (**fails** if not).
- `primary_action_maps` — every primary action maps to an API or is frontend-only.
- `api_mapped_to_screen` — every API dependency maps to a screen (warns if not).
- `do_not_build_present` — DO_NOT_BUILD exists (**fails** if not).
- `venture_scale_breakdown` — Venture Scale Score has an evidence/assumption breakdown.
- `no_fake_tam` — no fabricated TAM / unsupported unicorn claims in venture docs.

These run **only** when the blueprint/venture data is attached, so existing packs
and the canonical 27 documents remain unaffected.

## How it is generated & persisted

- During `PackService.generate()`, the blueprint is derived from the pack context
  and persisted to the `BuildBlueprint` table (one per pack, latest wins).
- `GET /workspaces/:ws/packs/:id/build-blueprint` returns it (regenerating from
  context if absent); `POST …/build-blueprint/regenerate` rebuilds it.
- Permissions: `pack:read` to view, `pack:generate` to regenerate.

## Pack integration (backwards-compatible)

The blueprint surfaces in packs as four **optional** documents appended to
build-oriented depths (never part of the required 27): `venture_thesis`,
`breakout_opportunity_memo`, `build_blueprint`, `do_not_build`. The structured
JSON/YAML lives in the `BuildBlueprint` entity and exports.

## Exports / AI-Agent bundle

The AI-Agent Engineering Bundle now ships implementation-ready files:
`VENTURE_THESIS.md`, `BUILD_BLUEPRINT.md`, `SCREEN_CONTRACTS.json`,
`STATE_MATRIX.json`, `API_TO_SCREEN_MAP.yaml`, `COMPONENT_CONTRACTS.json`,
`PERMISSION_MATRIX.json`, `ANALYTICS_EVENTS.json`, `DO_NOT_BUILD.md`,
`VALIDATION_RULES.md`, `EMPTY_LOADING_ERROR_STATES.md`. The Markdown ZIP adds a
`10_blueprint/` folder. `README_FOR_AGENT.md` instructs the agent to implement
screens from `SCREEN_CONTRACTS`, never invent screen logic, keep unresolved
questions unresolved, treat assumptions as non-facts, and not build anything in
`DO_NOT_BUILD.md`. See [EXPORTS.md](EXPORTS.md).

## Web UI

- **Niche detail → Venture thesis tab:** the four separate scores, thesis
  sections (with evidence/assumption flags), kill reasons, what must be true,
  validation experiments and the venture-scale dimension table.
- **Pack workspace → Build Blueprint panel:** Build Readiness score + breakdown +
  warnings, screen contracts with state coverage, API→screen map and
  DO_NOT_BUILD. Flat 2D, no gradients, no chat, no app-generation CTA.
